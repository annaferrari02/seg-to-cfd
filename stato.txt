---------------------------------------------------------------------
1. OBIETTIVO
---------------------------------------------------------------------

Automatizzare (con controllo umano nei punti giusti) la pipeline che
porta una segmentazione aortica fino a una simulazione CFD, passando per
tre software diversi:

  - 3D Slicer   -> creazione mesh / centerline        (passo 1, da definire)
  - ParaView    -> scale, triangulate, clean          (passo 2)
  - SimVascular -> faces, meshing, boundary conditions (passi 3-5)
  - svMultiPhysics -> il solver CFD                    (passo 5, ~8-10 h/pz)

Si parte da un "datalake" con una cartella per paziente (pz000, pz001, ...),
ognuna contenente la segmentazione / il modello di input. La pipeline deve:
  - gestire piu' pazienti;
  - permettere l'intervento umano (es. verificare le faces del "wall");
  - se un paziente crasha, segnalarlo e PROSEGUIRE con gli altri.


---------------------------------------------------------------------
2. ARCHITETTURA SCELTA (in breve)
---------------------------------------------------------------------

Ogni paziente e' una MACCHINA A STATI indipendente. Un ORCHESTRATORE
"stateless" (senza memoria propria) scandisce il datalake, legge lo stato
di ogni paziente da un file, e decide la prossima azione. Tutto lo stato
vive su disco (non in memoria): questo rende il sistema riavviabile,
ispezionabile e resistente ai crash.

Tre proprieta' guida:
  - ISOLAMENTO: lo stato e' per-paziente, quindi il guasto di uno non
    ferma gli altri.
  - STATO SU FILE: nessun database; il filesystem del datalake E' il
    database.
  - ORCHESTRATORE STATELESS: si puo' spegnere e riavviare in qualsiasi
    momento, ricostruisce cosa fare rileggendo i file di stato.

Le simulazioni (8-10 ore) vivranno in una CODA SEPARATA, per non bloccare
il resto del flusso (questa parte non e' ancora stata costruita).

4. COSA E' STATO COSTRUITO FINORA
---------------------------------------------------------------------

E' stato realizzato e VERIFICATO il "fondamento": il minimo che permette
di iscrivere un paziente alla pipeline e leggerne lo stato, SENZA ancora
lanciare alcun software esterno.

File creati (tutti nel MONDO 1):

  src/cfdpipe/ledger.py
      Il "registro di stato". Sa solo due cose:
        (a) quali stati puo' avere uno stadio (enum StageStatus:
            pending, running, awaiting_human, done, failed);
        (b) leggere/scrivere il file status.json in modo ATOMICO.
      Scrittura atomica = scrive prima un file temporaneo, poi lo
      rinomina; se il processo muore a meta', il status.json originale
      resta intatto (mai un file corrotto).
      NB: il ledger NON conosce l'ordine degli stadi. E' voluto:
      cambiare la pipeline non tocca la persistenza.

  src/cfdpipe/patient.py
      Astrazione su una cartella pz***. Conosce i percorsi standard
      (input .vtk, work/, preview/, sim/, status.json) e delega al
      ledger. Metodi principali:
        - initialize(): crea il status.json di un pz nuovo. E'
          idempotente (se esiste, lo ritorna senza resettarlo) e
          controlla che l'input esista.
        - set_stage(): unico modo per cambiare stato; appende sempre
          una riga di "history" -> tracciabilita' completa.
        - discover(): elenca tutti i pz nel datalake.

  src/cfdpipe/cli.py
      L'interfaccia a riga di comando. Per ora due comandi: init e
      status (spiegati sotto). Legge la posizione del datalake dalla
      variabile d'ambiente CFDPIPE_DATALAKE.

  pyproject.toml
      Descrive il pacchetto. Fa due cose all'installazione:
        - rende "cfdpipe" importabile;
        - crea il comando da terminale "cfdpipe".

  __init__.py, .gitignore
      Package marker + esclusione di datalake/, logs/ e file .vtk/.vtp
      dal versionamento (sono dati pesanti, non codice).

5. COM'E' FATTO IL LEDGER (status.json)
---------------------------------------------------------------------

Ogni paziente ha un file status.json nella sua cartella. Esempio reale
subito dopo "cfdpipe init pz000":

  {
    "schema_version": 1,
    "patient_id": "pz000",
    "stage": "paraview",        <- lo stadio da eseguire (il prossimo)
    "status": "pending",        <- il suo stato: in coda, non iniziato
    "updated_at": "2026-08-04T07:58:52+00:00",
    "artifacts": {},            <- file prodotti (nome logico -> path)
    "history": [                <- storia di tutte le transizioni
      { "stage": "ingest", "status": "done",
        "at": "...", "message": "pz inizializzato" }
    ]
  }

Logica dei due campi centrali:
  - "stage" punta sempre allo stadio DA FARE, non a quello gia' fatto.
    Appena il pz e' iscritto, il prossimo lavoro e' ParaView (passo 2),
    quindi stage = "paraview".
  - "status" e' lo stato di quello stadio. Subito dopo init e'
    "pending" perche' init ISCRIVE, non ESEGUE: nessuno ha ancora
    toccato ParaView.

Ciclo di vita previsto di uno stadio (quando ci sara' l'orchestratore):
  pending  -> in coda, lavoro pronto ma non preso in carico
  running  -> l'orchestratore ha lanciato il software, sta girando
  done     -> finito bene E output validato -> stage avanza al successivo
  failed   -> errore -> il pz resta flaggato, gli altri proseguono
  awaiting_human -> fermo in attesa di revisione (es. faces del wall)


---------------------------------------------------------------------
6. I COMANDI DISPONIBILI
---------------------------------------------------------------------

  cfdpipe init <pz>
      Iscrive un paziente. Controlla che la cartella e l'input esistano,
      poi CREA il status.json (stage=paraview, status=pending).
      Comando che SCRIVE. Idempotente. Fallisce in modo pulito se manca
      l'input (nessun traceback, solo un messaggio ed exit code 1).

  cfdpipe status [pz]
      Mostra lo stato. Senza argomento -> tabella di tutti i pz.
      Con argomento -> solo quel paziente. Comando in sola LETTURA.

  Notazione: <pz> = argomento obbligatorio; [pz] = argomento opzionale.

7. COME SI INSTALLA E SI LANCIA
---------------------------------------------------------------------

Una volta sola (creazione ambiente + installazione):
linux: 
  python3 -m venv .venv
  source .venv/bin/activate          # il prompt mostra (.venv)
  pip install -e .                   # editable: il codice e' collegato,
                                     # non copiato -> le modifiche ai
                                     # moduli sono attive senza reinstallare
windows: 
  python -m venv .venv
  .venv\Scripts\activate
  pip install -e .

Ogni sessione di lavoro (nuovo terminale):

  source .venv/bin/activate
  export CFDPIPE_DATALAKE=$(pwd)/datalake   # dove sta il datalake

Test del fondamento su un paziente:

  mkdir -p datalake/pz000
  cp /percorso/al/lumen_tree_cfd_cap.vtk datalake/pz000/
      # (per solo test infrastruttura basta un file placeholder:
      #  il fondamento controlla che l'input ESISTA, non lo legge)
  cfdpipe init pz000
  cfdpipe status
  cat datalake/pz000/status.json

Semaforo verde atteso: init stampa "stage=paraview status=pending",
status mostra pz000 in tabella, e il json contiene la riga di history
"ingest / done".

Attenzione: "cfdpipe init ..." funziona solo DOPO "pip install -e .".
Senza installare, l'equivalente e':
  PYTHONPATH=src python3 -m cfdpipe.cli init pz000
